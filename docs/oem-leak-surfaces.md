# OEM leak-surface manifest

This document is the human-readable pointer to the canonical OEM leak-surface
manifest. The canonical, machine-readable manifest lives at
[`t/fixtures/oem-leak-surfaces.json`](../t/fixtures/oem-leak-surfaces.json) and is
consumed directly by the CI-gated test
[`t/unit/oem_no_vendor_leak.js`](../t/unit/oem_no_vendor_leak.js).

## Why this exists

OEM-04 requires that under a valid `custom_branding` entitlement no vendor trace
(`LeavePilot` / `Leave Pilot` / `TimeOff` / `timeoff.management`) reaches ANY
rendered surface. The brand surfaces are DYNAMIC (`{{branding.name}}`,
`branding.getEmailFrom()`, the iCal PRODID, the web manifest, etc.), so a static
`.hbs` grep finds nothing — the regression guard must RENDER each surface under a
sentinel custom brand and assert the sentinel IS present AND the vendor literal
is ABSENT.

Per decision **D-08** (grep-before-test, committed in repo, CI-gated every PR),
the surface list is generated by grep over the vendor strings BEFORE the test is
written, committed to the repo as a fixture, and walked by the test on every PR
via `.github/workflows/core-ci.yml` (`npm run test:coverage` runs
`nyc mocha --recursive t/unit`). This is the same watchdog-with-teeth convention
used by `license_consistency`, `env_read_invariant`, and
`locales_no_brand_literal`.

## What the manifest covers

The JSON fixture has four sections:

- **`dynamic[]`** — rendered surfaces that read `branding.get()` /
  `branding.getEmailFrom()` and must be RENDERED under a sentinel custom brand.
  The test iterates EVERY entry and asserts BOTH custom-PRESENT and
  vendor-ABSENT. Covers the layout (favicons, `<title>`), navbar, footer
  copyright, the `/manifest.webmanifest` route, the login page title, the iCal
  feed PRODID/X-WR-CALNAME, the email `From:` address, and the OEM-suppressed
  license-status partial.
- **`hardcoded[]`** — rendered literals that do NOT flow through `branding.get()`
  (tracked with a before/after disposition). Today this is a single entry: the
  SSO `client_id` input placeholder, which carried the vendor domain and has
  been neutralized.
- **`excluded[]`** — surfaces that carry the vendor string legitimately or never
  render to an end user, each with a one-line rationale. This includes the brand
  layer itself (`DEFAULT_BRANDING` is the fallback shown only when OEM is NOT
  active), the render-mechanism files (`lib/view/helpers.js`, SSR wiring), the
  login host-comparison logic, internal storage keys, and — per decision **D-11**
  — the `window.timeoff` / `timeoff-config` / `timeoff-theme` JS runtime
  namespace (a devtools-observable code identifier, not rendered text; renaming
  it is a separate large phase).
- **`scanStrings[]`** — the vendor strings the manifest was grep-generated over.

## Keeping the manifest honest (Pitfall-5)

A static manifest goes stale silently: a new `branding.get()` consumer added
later but never entered into the manifest leaves the leak test green for the
wrong reason. The test therefore carries a COMPANION GREP (modeled on
`env_read_invariant.js`): it scans `lib/` and `app.js` for every
`branding.get()` / `getEmailFrom()` / `brand.get(` consumer and FAILS the build
if any consumer is not accounted for in `dynamic[]` or `excluded[]`. The
manifest cannot silently go stale, and its teeth assert a manifest surface
genuinely consumes `branding.get()` so the allowlist is never a phantom.

## Editing the manifest

When you add a new brand-bearing rendered surface:

1. Add it to `dynamic[]` (with `renderMethod: handlebars|http|email`) so the test
   renders and asserts it, OR
2. Add it to `excluded[]` with a one-line rationale if it is not a rendered
   surface (an internal key, a render mechanism, a logic-only check).

The companion grep will fail the build if you forget — that is the point.
